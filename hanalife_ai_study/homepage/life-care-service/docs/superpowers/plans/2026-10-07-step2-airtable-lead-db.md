# STEP 2 — 상담 신청 폼 → Airtable 고객 DB 연결 실습 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (또는 subagent-driven-development). 체크박스(`- [ ]`)로 진행을 추적한다. 이 계획은 수업 실습용이므로 각 Task는 "수강생이 직접 눈으로 확인하는 검증"으로 끝난다.

**Goal:** `index.html`의 "상담 신청하기" 폼이 제출되면 Airtable `Leads` 표에 한 줄이 쌓이게 한다(로컬 `localhost:3000`에서 끝까지 확인).

**Architecture:** 브라우저 → `POST /api/lead`(로컬은 `server.js`, 배포는 Vercel 서버리스) → 서버가 재검증·스팸방어 후 Airtable REST API 호출. 토큰은 `.env`에만 두고 브라우저에는 절대 노출하지 않는다. 표·필드·뷰는 Airtable 커넥터(MCP)로 Claude가 대화만으로 만든다.

**Tech Stack:** Node.js(서버), Airtable REST API + Personal Access Token, Airtable MCP 커넥터(OAuth), 기존 정적 `index.html`.

**Spec:** `C:\mino\project\hanalife_ai_study\0_자료\DB 연결하기.pdf` (8쪽, "PART 5 · STEP 2")

## Global Constraints (PDF 원문 그대로)

- 표 1개, 표 이름 `Leads`(영문), 필드명은 한글. 베이스 이름 `고객관리`.
- 토큰 스코프는 `data.records:read`, `data.records:write` 2개만. `schema` 권한 금지. 접근 범위는 베이스 1개만.
- `.env`에는 `AIRTABLE_TOKEN`, `AIRTABLE_BASE_ID` 2개. 커밋 금지.
- 엔드포인트 `POST /api/lead`. 유입경로 `홈페이지`, 상태 `신규`는 서버가 채운다.

- 저장 **성공했을 때만** "신청이 접수되었습니다" 표시. 실패 시 입력값 유지 + 안내.
- 공유 뷰(Share view) 링크 생성 금지. 개인정보 표이므로.
- 기존 폼 디자인은 그대로 유지.
- 인터넷 배포는 STEP 3. 이번 범위에 포함하지 않는다.

## Review Focus (PDF가 말하지 않지만 실제로 터질 입력)

1. 연락처에 하이픈 없음/있음 혼용(`01012345678` vs `010-1234-5678`): 서버가 어느 쪽이든 받고 저장 형식은 하나로 통일하는가.
2. 문의내용 매우 긴 입력·줄바꿈·이모지: Airtable 긴 텍스트로 깨지지 않고 저장되는가.
3. 폼 값이 표 선택지와 다른 경우(개발자도구로 조작): 서버가 400으로 거절하는가(Airtable에 임의 선택지가 생성되지 않는가).
4. `.env` 누락 상태로 서버 기동: 시작 시점에 명확한 메시지로 멈추는가(제출 시 500이 아니라).
5. Airtable 장애/429: 사용자에게는 "잠시 후 다시" 안내, 입력값 유지, 서버 로그에는 원인 기록.
